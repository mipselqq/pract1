## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
| :--- | :--- | :--- |
| customer | custkey, name | Join по custkey, вывод клиента. |
| orders | orderkey, custkey, orderdate, totalprice | Join по ключам заказа и клиента, вывод даты и цены, сортировка. |
| lineitem | orderkey, quantity; linenumber для очистки | Сумма quantity по заказу, фильтр строго >300; контроль уникальности позиции по (orderkey, linenumber). |

Исходный [Q18](sql/q18_reference.sql) сначала выбирает заказы с суммарным количеством больше 300, затем соединяет customer, orders и lineitem, выводит до 100 заказов по убыванию totalprice и дате. В Silver сумму по заказу вычислил заранее, чтобы в Gold не соединять повторно все позиции. При уникальных ключах orderkey/custkey результат сохраняется; сравнение с исходным SQL показало совпадение всех строк. В конец сортировки добавил orderkey, чтобы заказы с одинаковыми ценой и датой всегда шли в одном порядке. Одна строка результата соответствует одному заказу.

Это физический объём файлов, а не оценка логического размера через SHOW STATS. DDL, схемы и свойства сохранены в [results/layers.json](results/layers.json).

## 5. Тесты производительности

Стенд: Intel(R) Core(TM) i9-9900K CPU @ 3.60GHz, 16 логических CPU, 15.55 ГиБ RAM, Linux, один узел Trino. Версии образов, их digest и SHA-256 JAR сохранены в [environment_details.json](results/environment_details.json). Эксперименты выполнялись последовательно на одном компьютере.

Формат задаётся свойством таблицы `WITH (format=...)`, кодек - свойством сессии `compression_codec`. Реальные свойства проверены через `$properties`. Две шкалы времени разделены: **CLI wall** - perf_counter вокруг клиента вместе с его запуском; **server elapsed** - разность end и started из `system.runtime.queries`. Очередь, анализ и планирование сохранены отдельно. Server elapsed включает работу сервера по обработке запроса и не является CPU time.

### 5.1. Сжатие на Bronze - точный запрос варианта Q18

Подготовлены два полных входа по три таблицы: raw_lineitem/raw_orders/raw_customer с суффиксами gzip и zstd. В каждом варианте один кодек применяется ко всем трём таблицам. Запускается исходный SQL Q18 с заменой только имён таблиц. После отдельного прогрева выполнено пять повторов на вариант с перемешиванием порядка, seed=42. Каждый ответ совпал с Gold.

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
| :--- | :--- | ---: | :--- |
| GZIP | 0.564 с, медиана 5 запусков | 193.79 | Занимает на 5.50 МБ меньше ZSTD, но запись трёх таблиц дольше: 25.877 с. |
| ZSTD | 0.564 с, медиана 5 запусков | 199.29 | Выбрал для рабочих слоёв: запись заняла 13.399 с, а медиана Q18 такая же, как у GZIP. |

Подробные результаты с диапазоном времени и затратами на запись:

| Сжатие Bronze | Q18 server, медиана, с | Диапазон 5 запусков, с | CLI wall, медиана, с | Все 3 таблицы Bronze, МБ | Сумма времён записи 3 таблиц, с |
| :--- | ---: | ---: | ---: | ---: | ---: |
| GZIP | 0.564 | 0.561-0.614 | 1.405 | 193.79 | 25.877 |
| ZSTD | 0.564 | 0.533-0.604 | 1.424 | 199.29 | 13.399 |

Размер сценария - сумма data-файлов его трёх таблиц, а не всего бакета с одновременно хранящимися экспериментами. Время записи каждой таблицы измерено при одной CTAS; сумма не является повторным статистическим измерением. Размеры, числа строк, кодеки и времена по каждой таблице - [bronze_variants.json](results/bronze_variants.json).

**Вывод:** GZIP экономит место, ZSTD в этой записи потребовал меньше времени. Диапазоны Q18 перекрываются: наблюдаемые времена не дают устойчивого преимущества одному кодеку на прогретом sf1. Выбор ZSTD для рабочих слоёв обоснован компромиссом размера и стоимости записи.

### 5.3. Пять повторных прогретых агрегаций

Каждый вариант предварительно прогрет отдельным запуском. Сохранены все 40 замеров, queue/analysis/planning и query_id: [repeated_runs.csv](results/repeated_runs.csv), [сводка](results/repeated_summary.json). Все ответы проверены; суммы double сравнены с допуском 1e−10 относительно и 1e−4 абсолютно.

| Вариант | Повторов | Server, медиана, мс | Min-max, мс | Выборочное σ, мс | CLI wall, медиана, с |
| :--- | ---: | ---: | ---: | ---: | ---: |
| parquet_none | 5 | 169 | 150-204 | 20.7 | 1.023 |
| parquet_snappy | 5 | 186 | 176-212 | 14.3 | 1.107 |
| parquet_gzip | 5 | 209 | 206-221 | 6.3 | 1.053 |
| parquet_zstd | 5 | 173 | 163-189 | 9.4 | 1.015 |
| orc_none | 5 | 329 | 268-360 | 34.8 | 1.173 |
| orc_snappy | 5 | 318 | 287-372 | 31.5 | 1.154 |
| orc_gzip | 5 | 366 | 363-444 | 35.7 | 1.265 |
| orc_zstd | 5 | 362 | 336-371 | 14.4 | 1.196 |

Ответы на вопросы гайда:

1. **Размер.** Минимум - Parquet/GZIP (150.63 МБ). Экономия к Parquet/NONE: GZIP 59.6%, ZSTD 58.6%. ORC/ZSTD больше Parquet/ZSTD на 4.5% на этом плоском наборе.
2. **Запись.** Parquet/GZIP записался в 2.28 раза дольше Parquet/NONE. По отношению к Parquet/ZSTD дополнительное сжатие GZIP - только 2.4%; для частых обновлений выбран ZSTD. Это вывод из одной записи, а не оценка среднего времени CTAS.
3. **Чтение.** Минимальная медиана прогретой агрегации - 169 мс у Parquet/NONE; Parquet/ZSTD - 173 мс, их диапазоны перекрываются. Здесь чтение из кэша уменьшает пользу сжатия. При ограничении дискового I/O сжатый файл может выигрывать за счёт меньшего объёма чтения даже с затратами на распаковку.
4. **Компромисс.** ZSTD выбран для основных слоёв по сочетанию размера и записи. SNAPPY - кандидат для частой быстрой записи, но в этой первичной серии его преимущество над ZSTD по записи невелико. GZIP полезен для редких перезаписей при приоритете объёма; на этом наборе его дополнительная экономия мала.
5. **Метаданные и кэш.** Манифест Parquet/ZSTD - 9555 байт, 0.0062% объёма data-файлов. Это только манифест, остальные metadata JSON/manifest list в число не входят. Повторные запросы устраняют часть затрат на инициализацию и кэши; оба режима и их ограничения указаны отдельно.

### 5.4. Параллельный запуск Gold

Скрипт parallel_gold.py сначала выполняет один запрос к Gold, затем запускает 10 таких запросов через ThreadPoolExecutor. Все 10 ответов совпали, ошибок 0. Один запрос - 0.867 с, пачка из 10 - 2.992 с; throughput - 1.15 и 3.34 запроса/с соответственно (рост 2.90×). Скрипт - [parallel_gold.py](scripts/parallel_gold.py), результат - [parallel_gold.json](results/parallel_gold.json). Gold содержит 57 строк, поэтому здесь велик вклад запуска CLI и обмена с сервером: результат характеризует параллельные обращения к маленькой витрине, не пропускную способность полного скана TPC-H.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
| :--- | :--- |
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | S3-хранилище и вычисления масштабируются независимо, разные движки читают открытые файлы. Iceberg добавляет схему, атомарные изменения и снапшоты. Для небольшого приложения обычная БД проще; цель этой работы - проверить многослойное хранение и независимый доступ движков. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Добавлена review_note varchar: у старых 57 строк NULL. Затем выполнено RENAME review_note → audit_note → review_note. Число строк сохранилось; списки путей и размеров data-файлов до/после совпали, список снапшотов не изменился. DDL меняет метаданные схемы без переписи файлов. |
| Пример скрипта восстановления данных из снапшота (time travel) | [evolution.py](scripts/evolution.py) читает первый snapshot_id и выполняет CTAS из FOR VERSION AS OF в bench.lakehouse.restored_lineitem. Восстановлено 6 001 215 строк; совпали count, sum(orderkey) и sum(quantity) со старым снимком. Текущий Bronze сохранил 6 001 217 строк. |

Выполненный SQL восстановления этой установки (при новой установке ID вычисляет скрипт):

```sql
CREATE TABLE bench.lakehouse.restored_lineitem WITH (format='PARQUET') AS SELECT * FROM bronze.lakehouse.raw_lineitem FOR VERSION AS OF 8918826211794721819;
```

Первый snapshot_id - 8918826211794721819; восстановление заняло 6.717 с. Восстановленную таблицу сохранил в bench. Результаты проверки и выполненный SQL: [evolution.json](results/evolution.json), [recovery.sql](results/recovery.sql).
